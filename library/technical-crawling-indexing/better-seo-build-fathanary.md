# better-seo-build

Pairs with `better-seo` (`/seo-audit`). **This skill builds; that one measures.**
Audit a URL to score a live page; build SEO config into a project that does not
have it yet. If the user has a live site and wants to know what is wrong, that
is `/seo-audit`, not this.

## The one rule

Never invent the site's facts. Origin, site name, page titles and descriptions
come from the project files or from the user. Anything you had to guess stays
marked `TODO` in the output so it cannot ship silently.

## Step 1: look at the project before writing anything

Read the repo. Do not assume a framework.

```bash
ls
cat package.json 2>/dev/null || cat _config.yml 2>/dev/null || cat hugo.toml 2>/dev/null
```

Then run the scaffolder. It detects the framework, plans the edits, and writes
nothing unless told to:

```bash
python <skill-dir>/scripts/seo_build.py --root .
python <skill-dir>/scripts/seo_build.py --root . --site https://example.com --write
```

Output is JSON: detected `framework`, the `evidence` files it used, `site` and
whether that origin came from `package.json` or is a placeholder, then one entry
per artifact with an `action`.

The scaffolder never overwrites. A path that already exists is reported as
`skipped (exists)`; read that file and edit it by hand instead.

## Step 2: fill in what only the user knows

The generated files carry placeholders on purpose. Resolve them with the user
before finishing:

| Placeholder | Ask for |
|---|---|
| `https://example.com` | the real origin, including scheme and `www` decision |
| `Replace with a 50-60 character title` | the page's primary phrase |
| `Replace with a 120-155 character description` | what the page delivers, to whom |
| `One sentence describing what this site is` | used by `llms.txt` |

Do not leave a guessed domain in a shipped file. A wrong canonical is worse than
a missing one.

## Step 3: the checklist this skill must satisfy

Each item is required; the scaffolder covers the file-shaped ones.

- [ ] **`robots.txt`** exists, allows `*`, and references the sitemap. AI
      crawlers (`GPTBot`, `OAI-SearchBot`, `PerplexityBot`, `ClaudeBot`) are
      allowed unless the user explicitly wants out of AI search.
- [ ] **`sitemap.xml`** is generated by the framework, not hand-maintained.
      Framework targets get a generator; static targets get a stub to fill.
- [ ] **`llms.txt`** only if the links in it are real. It is not a standard and
      not a ranking factor; say so if asked.
- [ ] **`<title>`** 50-60 chars, one per page, unique across the site.
- [ ] **`<meta name="description">`** 120-155 chars, one per page.
- [ ] **`<link rel="canonical">`** absolute, self-referencing on every page.
- [ ] **Open Graph + Twitter** tags present so links unfurl.
- [ ] **JSON-LD** `WebSite` + `WebPage` site-wide; add `Article`, `Product`,
      `FAQPage`, `LocalBusiness` per page type where they apply.
- [ ] **`<html lang="...">`** set.
- [ ] **One `<h1>`** per page matching intent.
- [ ] Server-rendered body text, not JS-only.

## Step 4: verify before handing back

Never claim it works because the files were written.

```bash
python <skill-dir>/scripts/seo_build.py --root .        # all steps should read skipped/exists now
```

Then audit what you produced. If the project builds:

```bash
npm run build && npm start            # or the project's own command
python <audit-skill-dir>/scripts/audit.py http://localhost:3000
```

If it cannot be served, audit the generated HTML file directly:

```bash
python <audit-skill-dir>/scripts/audit.py --fixture dist/index.html
```

Report the score before and after, and say plainly if you could not run it.

## Framework notes

| Framework | robots / sitemap | Head tags |
|---|---|---|
| Next.js App Router | `app/robots.ts`, `app/sitemap.ts` | `export const metadata` |
| Next.js Pages | `public/robots.txt`, `public/sitemap.xml` | `next/head` |
| Astro | `public/robots.txt`, `src/pages/sitemap.xml.ts` | component in `<head>` |
| SvelteKit | `static/robots.txt`, `src/routes/sitemap.xml/+server.ts` | `<svelte:head>` |
| Nuxt | `public/robots.txt`, `server/routes/sitemap.xml.ts` | `useHead` |
| Hugo | `static/robots.txt`, `layouts/sitemap.xml` | `layouts/partials/seo.html` |
| Jekyll | `robots.txt`, `sitemap.xml` | `_includes/seo.html` |
| WordPress | `robots.txt` (core serves sitemap) | theme / `wp_head` |
| Static HTML | `robots.txt`, `sitemap.xml` | edit `<head>` or use `--inject` |

Prefer the framework's own mechanism over a static file when one exists. A
hand-written `sitemap.xml` goes stale; a generated one does not.

## Guardrails

- Never invent traffic, rankings, backlink, or competitor data.
- Never promise a ranking or an AI citation.
- Never recommend cloaking, hidden text, doorway pages, or link schemes.
- Never add `noindex` to make a score look better.
- Never delete existing SEO work to make the output uniform. Merge, do not reset.
- Flag anything you could not verify instead of asserting it works.
